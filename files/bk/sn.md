# bk01 串口通信 SN 号与重发机制审计总结

> 审计日期：2026-10-19
> 范围：模组（EFR32）↔ MCU 的 SPP 协议（`55 AA` 帧），代码位于
> `src/misc/sp_protocol.cpp`（组帧/解析/校验）、`src/app/app_msg_mgr.cpp`（发送队列/重发）、
> `src/app/app_spm_mgr.cpp`（命令分发/ACK）
> 参考规范：用户提供的《串口通信 SN 号与重发机制设计要点》

## 1. 帧格式

```
55 AA | 01(版本) | SN(2B, 大端) | CMD(1B) | LEN(1B) | payload(LEN) | checksum(1B)
checksum = 前面所有字节（含 SN、payload）求和取低 8 位
```

注意：MCU 实现中 **SN 高字节被用作"重发标志"**（首帧=00，重发帧=01，低字节不变），
并非 16 位序列号。序列号实际是低字节。

## 2. SN 逻辑审计结论（多轮实测日志核对）

| 检查项 | 结论 |
|---|---|
| 模组 TX SN | 严格 +1 递增，重发不换号 ✓ |
| MCU 上报 SN | 低字节严格 +1（实测 0x00→0x0B 连续无跳号）✓ |
| MCU 高字节 | 重发标志：所有高字节=01 的帧都是紧邻前一帧的完整重复 |
| ACK | 双方均正确回带对方 SN，模组 1~2ms 内即回 ✓ |
| 双向撞号（如模组命令 SN 0x0004 与 MCU 上报 SN 0x0004 并存） | 协议允许（方向独立 + CMD 区分），实测 6+ 处撞号零误判 ✓ |
| "00 03 后出现 00 00"类疑问 | 两个方向各自独立计数器，MCU 上报从自己的初值起步，非异常 ✓ |

## 3. 规范对照（9 符合 / 4 偏差）

### 符合

| 规范条目 | 代码证据 |
|---|---|
| 重发 SN 不变 | `send_frame(true)` 重发 `cur_msg` 原始字节 |
| 新事务才 +1 | `get_increase_sn()` 仅在 `encode()` 时调用 |
| A/B 独立计数 | 模组 `cur_sn`、MCU 独立计数器 |
| B 首报用自己初值 | MCU 从 0 起步，不跟随模组 |
| ACK 回显对端 SN | `send_ack(type, sn)` |
| 有限重试 3 次 | `RE_SENT_MAX_NUM=2` → 1+2=3 发 |
| 校验和覆盖 SN+payload | `check_sum_buffer(rx_buffer, cur_idx-1)` |
| 校验失败丢弃不回 ACK | decode checksum err → 丢弃，等发送方超时重发 |
| 重要上报等 ACK 重发 | MCU 侧行为（0x12/0x08 实测重发） |

### 偏差（按危害排序）

| 条目 | 现状 | 危害 |
|---|---|---|
| 5.3 超时按对方最坏处理时间 | 保持 500ms（用户决定）。实测 MCU 电机忙时 0x11 回显最坏 ~1.07s | 每条窗帘控制命令发 2 遍（1 次重试），功能无损，属规范允许的正常重试 |
| 5.1/5.2 Retry 标志 + 接收去重 | 模组重发帧与首发字节级相同（无标志）；收到 MCU 重发帧会重新执行业务 | 当前上报幂等（同值写 Matter 层 no-op）无实害；未来非幂等命令需先补此机制（需 MCU 侧共同确认标志位定义） |
| 5.3 超限上报错误 | `re-sent reach to max` 后静默丢帧 | 窗帘控制失败时 Matter 侧无感知（需定义应用层错误通知路径，可排期） |
| 5.4 SN 回绕 | cur_sn 16 位回绕无保护 | 当前无去重表暂无害；补去重时必须用"最近 SN 集合"判定，不能用大小比较 |

## 4. 已修复的代码 bug（3 处）

1. **`sp_protocol.cpp` `check_sum_buffer`**：`uint8_t temp;` 未初始化即累加（UB，靠寄存器恰为 0 才工作）→ `= 0`
2. **`app_msg_mgr.cpp` `set_ack_timeout`**：下限钳位分支写重（两个 `> MAX`），`ACK_TIMEOUT_MS_MIN` 从未生效 → 改为 `< MIN`
3. **`app_spm_mgr.cpp` `spp_app_event_CurtainPercentCtrl`**：MCU 对 0x11 命令的应答是"原样回显"（同 SN 同 payload），原代码误解析为位置上报，导致 `CurrentPosition` 瞬间跳到目标值、污染位置状态（会破坏 TC-WNCV-3.2 收敛判断）→ 改为仅 `remove_pending_msg()`（与 0x10 处理器一致）

## 5. 实测验证结论（500ms 超时固件）

- 模组命令 SN 0x0000→0x0006 严格递增；每条 0x11 控制命令恰好发 2 次（首发 + 1 次重试），MCU echo 到达后清 pending，无 tx_queue full
- 方向语义定案：**MCU percent = 关闭度**（0=全开 100=全关），模组发送换算 `100 - target/100` 与之匹配；多次命令后位置上报均真实收敛
- 0x10（开/关/停）：MCU 固件未实现（无动作）；**0x10 0x01 停止命令可用**；窗帘控制一律走 0x11
- identify（kActuator）：Start 按当前位置区分方向走全程（偏开→关到 0%，偏关→开到 100%），Stop 发 0x10 0x01 停机

## 6. 遗留问题（MCU 固件侧）

| 问题 | 证据 | 建议 |
|---|---|---|
| 0x12 位置上报、0x08 充电档位**每条必重发一次**（模组 1~2ms 内已 ACK） | 各日志中每条 0x12/0x08 后 500ms 恒跟一条 hi=01 重复帧；0x06/0x07 从不重发 | MCU 检查对这两类上报的 ACK 匹配逻辑 |
| 0x10 开/关命令未实现（0x01 stop 可用） | 帧发出后无动作、无应答 | MCU 补实现或协议文档标注不支持 |
| 产品信息 JSON 缺闭合引号：`{"p":"BK001","v":"1.2.6}` | 模组严格解析失败，靠 fallback 正则提取 1.2.6 | MCU 补引号，模组去掉 fallback 依赖 |
| MCU 对 0x11 回显延迟最坏 ~1.1s（电机忙时） | 模组 500ms 超时下每条命令重发 1 次 | 若希望单次送达：MCU 加快回显，或双方约定提高模组该类超时 |
